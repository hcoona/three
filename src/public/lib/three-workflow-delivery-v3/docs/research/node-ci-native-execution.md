# Node CI Native Execution Qualification

## Purpose and Authority

This protocol becomes executable only after protected repository acceptance
under the [contraction Wave](../../../../../../docs/delivery-wave.md). Its consumer
is the replacement application's native Node check boundary before workflow cutover.
It tests actual planning, native NBGV stamping, original packaging and fresh
public API consumption together, rather than re-proving PNPM or NBGV.
The accepted contraction Wave supplies the effects ceiling; protected delivery
of this concrete protocol is required before its first sequence. Earlier npm,
NuGet, Python, Ruby and native-reader campaigns remain completed and spent.

## Finite Sequence and Cumulative Bounds

After preparation, run one actual `ci plan-node` on the accepted base and the
single exact candidate, selecting only the README change. Do not enable full
mode or replace a failed plan. It must select all five adopted checks with their
complete package/build/output associations and exact candidate identity.
Keep the resulting plan immutable for both candidate executions.

Run `ci run-node` once per candidate materialization, for at most two
same-candidate sequences. Both start with clean tracked HEAD, the recorded local
ref/history context, unchanged tools/locks and the external compiled controller.
Each executor owns fresh scratch only; no source import or warmed consumer cache
can supply an installed result. Native build, pack lifecycle and installation
remain opaque CLI operations; do not replay scripts or synthesize a manifest.

Maximum preparation: three native local Git materializations, one local candidate
commit, three frozen offline/script-disabled PNPM installs, one .NET restore and
one no-restore build. Each preparation command is at most 300 seconds. Read-only
identity/input inventory is at most forty native queries of at most thirty
seconds each. Overall preparation is at most 1,800 seconds and 4 GiB owned state.

Planning is at most one process, 900 seconds, sixty PNPM queries of thirty seconds
each, twenty Git queries of thirty seconds each, and the selected managed NBGV
input/projection calls. These finite ceilings are checked against the exact
current seven-project roster before acceptance. No second extraction/resolver
is maintained. Exceeding native roster/shape limits stops the sequence.

Each adopted executor sequence permits seven outer command observations:
source build, independent source test, one pack, two typed packed-metadata
queries, one native original-tarball install and one Node public API assertion.
Build/test/pack/install each have the implemented 300-second deadline;
metadata/Node each have thirty seconds. Starting Git binding uses at most eight
thirty-second queries. A sequence is at most 1,500 seconds; the campaign is at
most 4,800 seconds including preparation and planning.

The nested reviewed product scripts are included: source build and native
prepack each invoke one stamp, totaling at most four bundled NBGV get-version
calls, four dotnet runtime-list calls and two local npm version commands per
sequence. Native postpack directly resets its placeholder. Node build/test and
public API assertions remain the exact reviewed scripts. Native wrapper runtime
selection is used as shipped. Source-derived call inventory is not a runtime
trace or proof that every child exited. Native child operations use their
finite deadlines and existing five-second cleanup. An inner cleanup failure is
retained as a failed check; the executor may finish other eligible independent
checks within that same reserved `ci run-node` invocation. Its terminal failure,
or caller-observed outer cleanup uncertainty, stops new campaign invocations.
These primitives do not prove a complete descendant exit barrier.

Archive limits are the implementation's 32 MiB compressed, 128 MiB expanded,
32 MiB per member, 1,024 members and 1 MiB each required manifest/payload.
Application command streams retain at most 33,554,432 characters. The concrete
caller applies a stricter 33,554,432-byte ceiling to each of its stdout/stderr
evidence logs: concurrently read supported process pipes, write only the bounded
prefix, and stop at the first excess. These are finite experiment/application
bounds, not universal npm validity rules.

## Expected Observations and Stops

All five planned checks must be present and passed. The planned official NBGV
npm projection must equal native packed metadata. Every original output must
retain its unit/build/output/role/kind, size and digest. Installed consumption
uses the complete original tarball, without source references or prewritten
consumer metadata, and must pass public package resolution and smokeMessage().
Read-only digest checks before/after inspection and installation must confirm
original bytes remain unchanged. Two successful same-candidate sequences may
compare original bytes as bounded reproducibility evidence; equality is not
required between distinct commits.

Reserve each whole preparation, planning or `ci run-node` invocation before
launch. A failed preparation or planning invocation stops the campaign. Within
its finite selected work, `ci run-node` preserves inner native/check failures,
skips their failed dependencies and may finish independent eligible checks,
including after an inner cleanup failure. That continuation is part of the
original invocation, without a retry or new sequence. The caller observes its
terminal result; a failed execution invocation consumes its position and stops
all later campaign invocations, including the second materialization.

Preserve nonzero, cancellation, timeout, invalid output, unsupported shape,
version disagreement, missing output, failed installed consumption, unexpected
external effect or exhausted bound. No rerun, fallback, source correction,
replacement candidate, publication or new slot follows. Read-only analysis of
the retained failure is permitted. A necessary native capability gap returns to
the owner before any changed design or operation.
