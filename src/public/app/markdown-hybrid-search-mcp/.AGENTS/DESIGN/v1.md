# Markdown Hybrid Search MCP — Design (v1)

## Summary

This subproject will implement an MCP server that builds a **one-shot, ephemeral local index** for Markdown corpora under one or more root folders provided via CLI arguments. The server provides **hybrid retrieval** by combining:

- **Vector retrieval** over semantic embeddings, and
- **Full-text retrieval** (BM25-style) over tokenized text.

The system is optimized for repeated queries during a single server run. It avoids brute-force full rescans per query.

## Goals

- Provide an MCP server that can be started with one or more corpus roots.
- Discover Markdown documents under those roots and build a local **temporary** index at startup.
- Support hybrid search with configurable weights and sensible defaults.
- Address **document length imbalance** so long documents do not dominate results.
- Handle Markdown that embeds code blocks (no multimodal/image support).

## Non-goals

- Image/multimodal indexing.
- Remote hosted databases or distributed indexing.
- Complex access control/tenanting.

## Interface

### CLI / Process arguments

The server process will accept:

- `--root <path>`: repeatable. One or more folder roots to scan.
- `--work-dir <path>`: optional working directory for temporary index storage (default: OS temp).
- `--reindex {force,off}`: whether to build the index on startup (default: build).

Azure OpenAI (Entra ID auth):

- `--azure-openai-endpoint <https://...>`
- `--azure-openai-embedding-deployment <deployment>`
- `--azure-openai-chat-deployment <deployment>`
- `--azure-openai-api-version <YYYY-MM-DD>`
- Optional: `--azure-tenant-id <tenant-guid>`
- `--include-glob/--exclude-glob`: optional filters (defaults include `**/*.md` and `**/*.markdown`).

Credential preference (resolved requirement):

- Prefer Azure CLI > Interactive Browser > Device Code.

### MCP tools

Expose an MCP tool set (names are placeholders; final names should align with repo conventions):

1. `search`
    - Input: `query: str`, `top_k: int`, optional filters (`roots`, `path_prefix`, `updated_after`, etc.)
    - Output: ranked results containing (at minimum):
        - `doc_id`, `path`, `title` (if derivable), `snippet`, `score`, plus per-channel scores (vector/text).

2. `get_document`
    - Input: `doc_id` or `path`
    - Output: stored metadata and optionally full content (or content window).

3. `stats`
    - Output: index stats (doc count, last indexing time, embedding deployment id, embedding dimensions, etc.).

## Data model

### Document-only indexing

For v1, the system indexes at **document** granularity only.

- Document: a Markdown file.
- Record metadata: `doc_id`, `path`, `mtime`, `size`, plus derived fields used for search.

Derived fields (recommended):

- `text_all`: Markdown rendered/normalized to plain text, including code blocks.
- `text_no_code`: a code-light representation for semantic embeddings.
- `code_signals`: a deterministic, compact representation of code blocks (commands, flags, errors, identifiers).
- `title`: best-effort title (e.g., first H1), optional.

### Storage backends

We need both full-text and vector indexes. Target design:

- **Preferred unified storage**: DuckDB in a temporary directory for the lifetime of the process. Use DuckDB features/extensions to support full-text search and vector similarity search.

Fallback if DuckDB vector/FTS packaging is problematic:

- SQLite for metadata + FTS5 for full-text.
- Vector indexing via either a SQLite vector extension (if available) or a dedicated embedded vector store.

Implementation should hide the chosen backend behind abstractions (e.g., `FullTextIndex` and `VectorIndex`).

## Index build pipeline

1. **Discovery**
    - Recursively enumerate Markdown files under all `--root` directories.
    - Record `path`, `mtime`, `size`, and a stable `doc_id` (e.g., hash of normalized absolute path + inode equivalent).

2. **Parsing (document-level)**
    - Produce two derived text views:
        - `text_all`: includes code blocks.
        - `text_no_code`: excludes (or strongly down-weights) fenced code blocks.
    - Extract deterministic `code_signals` from fenced code blocks.
    - Store code blocks with stable identifiers for optional retrieval/display:
        - `code_block_id = hash(path + block_index + content_hash)` (example scheme)

3. **Embedding (document-level)**
    - Compute embeddings using Azure OpenAI embeddings.
    - Default embedding input: `text_no_code`.
    - For `mode=mixed` (future option): embed `text_no_code + code_signals`.
    - Store embedding model identity and dimensions in index metadata for observability.

    Length imbalance mitigation for embeddings (no chunking):
    - Embed a **length-normalized representation** of the document (cap tokens/chars).
    - Suggested strategy: keep headings + first N tokens of prose (optionally plus tail), drop or down-weight code.

4. **Full-text indexing (document-level)**
    - Index `text_all` for keyword lookup (error messages, commands, API identifiers).

5. **Vector indexing (document-level)**
    - Index document embeddings.

6. **No incremental updates (v1)**
    - Build once at startup; do not watch or update during the process lifetime.

## Handling length imbalance (bias control)

Problem: if documents have very different lengths, vector embeddings computed from raw long text can become less representative, and text scoring can skew toward verbose documents.

Mitigations (document-level):

1. **Length-normalized embedding input**
    - Do not embed the entire file verbatim.
    - Use a bounded representation (headings + capped prose) so long documents do not dilute semantics.

2. **Length-aware scoring adjustment (optional)**
    - If needed, apply a mild penalty based on document length:
      $$\text{score} = \text{hybrid\_score} \cdot \frac{1}{1 + \alpha \log(1 + \text{doc\_chars})}$$

3. **Diversification (optional)**
    - Apply a light MMR-like diversification step over final results.

## Hybrid retrieval strategy

### Candidate generation

- Retrieve `k_text` candidates from full-text search over documents.
- Retrieve `k_vec` candidates from vector search over document embeddings.

### Coarse reranking via RRF (rank fusion)

Use Reciprocal Rank Fusion (RRF) to combine multiple ranked lists (e.g., full-text rank list and vector rank list) into a single coarse ranking.

For each candidate document $d$, compute:

$$\mathrm{rrf}(d) = \sum_{i \in \{\text{text},\text{vec}\}} \frac{1}{k + r_i(d)}$$

Where:

- $r_i(d)$ is the 1-based rank of document $d$ in channel $i$ (missing documents contribute 0 for that channel),
- $k$ is a smoothing constant (typical values are 50–60).

Notes:

- RRF is robust when channel score scales differ and avoids manual weight tuning.
- This design does not use a separate rerank model for fine reranking.

### Result shaping

- Results are already document-level.
- Provide a snippet derived from `text_all` around the best-matching region (implementation detail).

## Code blocks

- Code blocks are indexed in `text_all` for full-text search.
- For vector search, compute embeddings from `text_no_code` by default.
- Additionally compute and store `code_signals` (deterministic, local extraction) and retain `code_block_id` pointers for retrieval.
- Provide (future) query option `mode: {"docs","code","mixed"}`. Semantics: `docs` emphasizes prose; `mixed` includes code signals; `code` emphasizes code signals and relies on full-text for exact matching.

## Observability & operations

- Maintain an `index_meta` record:
    - corpus roots,
    - build timestamp,
    - embedding deployment id/name, dimension,
    - counts.
- Emit structured logs for:
    - index build duration,
    - docs indexed,
    - query latency breakdown (fts, vector, fusion).

## LLM-assisted retrieval (optional)

Use an Azure OpenAI chat/completions model to improve quality beyond pure hybrid retrieval.

Stages:

1. **Query rewrite / expansion**
    - Turn the user query into:
        - a keyword query for full-text, and
        - a semantic query for embeddings.
    - Expand abbreviations and normalize product/resource names.

2. **Answer synthesis (RAG)**
    - Compose a final answer with citations to document paths.

Data minimization principle:

- It is acceptable (privacy/compliance) to send messages to Azure OpenAI. Prefer sending only the user query and small candidate snippets when possible.

## Risks and constraints

- DuckDB full-text/vector capabilities and packaging may require careful dependency choices on Windows.
- Azure OpenAI embeddings and chat models require network connectivity and Entra ID credentials.
- One-shot indexing means startup time is the key UX constraint.
