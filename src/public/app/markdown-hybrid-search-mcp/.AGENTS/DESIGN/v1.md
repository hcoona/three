# Markdown Hybrid Search MCP — Design (v1)

## Summary

This subproject will implement an MCP server that builds a **one-shot, ephemeral local index** for Markdown corpora under one or more root folders provided via CLI arguments. The server provides **hybrid retrieval** by combining:

- **Vector retrieval** over semantic embeddings, and
- **Full-text retrieval** (BM25-style) over tokenized text.

The system is optimized for repeated queries during a single server run. It avoids brute-force full rescans per query.

This is the **first** version of the system and should remain **minimal**: prioritize correctness and a small feature set over extensibility.

## Goals

- Provide an MCP server that can be started with one or more corpus roots.
- Discover Markdown documents under those roots and build a local **temporary** index at startup.
- Support hybrid search with sensible defaults.
- Address **document length imbalance** so long documents do not dominate results.
- Handle Markdown that embeds code blocks (no multimodal/image support).

## Non-goals

- Image/multimodal indexing.
- Remote hosted databases or distributed indexing.
- Complex access control/tenanting.

## Interface

### CLI / Process arguments

The server process will accept:

- `--root <path>`: repeatable. One or more folder roots to scan.
- `--work-dir <path>`: optional working directory for temporary index storage (default: OS temp).
- `--reindex {force,off}`: whether to build the index on startup (default: build).

Azure OpenAI (Entra ID auth):

- `--azure-openai-endpoint <https://...>`
- `--azure-openai-embedding-deployment <deployment>`
- `--azure-openai-chat-deployment <deployment>`
- `--azure-openai-api-version <YYYY-MM-DD>`
- Optional: `--azure-tenant-id <tenant-guid>`
- `--include-glob/--exclude-glob`: optional filters (defaults include `**/*.md` and `**/*.markdown`).

Required in v1:

- `--azure-openai-embedding-deployment` (embeddings)
- `--azure-openai-chat-deployment` (LLM-assisted query rewrite/expansion)

Discovery rules (v1):

- Always ignore `.git/` directories.
- Ignore behavior is delegated to the installed `fd` implementation.
- Follow symlinks/junctions during enumeration.
- Enforce `--root` folders as hard boundaries on **real paths** (see “Symlink boundary rule”).
- Deduplicate files by normalized real path.

Implementation note (v1): record `fd --version` and the exact `fd` invocation in logs and/or `index_meta`.

Symlink boundary rule (v1):

- Follow symlinks/junctions, but only index a file if its `realpath` is within at least one provided `--root`.
- The stored/returned `path` is the **normalized real path** (as defined by `normalized_real_path`).
- Path-based filters such as `roots` and `path_prefix` apply to the normalized real path.

Credential preference (resolved requirement):

- Prefer Azure CLI > Interactive Browser > Device Code.

### MCP tools

Expose an MCP tool set (names are placeholders; final names should align with repo conventions):

1. `search`
    - Input: `query: str`, `top_k: int`, optional filters (`roots`, `path_prefix`, `updated_after`, etc.)
    - Output: ranked results containing (at minimum):
        - `doc_id`, `path`, `title` (if derivable), `snippet`, `score`.
        - Channel diagnostics (recommended for debuggability):
            - `text_rank` (nullable), `text_bm25` (nullable)
            - `vec_rank` (nullable), `vec_distance` (nullable)

2. `get_document`
    - Input: `doc_id` or `path`
    - Output: stored metadata and optionally raw Markdown content (or a content window).
    - Defaults and limits (v1):
        - Content format: raw Markdown.
        - Optional windowing parameters (recommended): `offset_chars` (default: 0) and `max_chars`.
        - Hard cap: `max_chars <= 200000`.
        - Include `truncated: bool` and `returned_chars: int` in the response when content is returned.

3. `stats`
    - Output: index stats (doc count, last indexing time, embedding deployment id, embedding dimensions, etc.).

## Data model

### Document-only indexing

For v1, the system indexes at **document** granularity only.

- Document: a Markdown file.
- Record metadata: `doc_id`, `path`, `mtime`, `size`, plus derived fields used for search.

`doc_id` (v1):

- `doc_id` is the SHA-256 hex digest of the UTF-8 bytes of `normalized_real_path`.
- `normalized_real_path` is defined as:
    1. `realpath(path)` (after following symlinks/junctions)
    2. Convert path separators to `/`
    3. On Windows: case-fold the full path (equivalent to `normcase`)
    4. Apply Unicode normalization (NFC)

Derived fields (recommended):

- `text_all`: Markdown rendered/normalized to plain text, including code blocks.
- `text_no_code`: a code-light representation for semantic embeddings.
- `code_signals`: a deterministic, compact representation of code blocks (commands, flags, errors, identifiers).
- `title`: best-effort title (e.g., first H1), optional.

### Storage backends

We need both full-text and vector indexes.

- **Unified storage (v1, no fallback)**: DuckDB (v1.4.3) in an owned temporary directory for the lifetime of the process. Use DuckDB extensions to support full-text search and vector similarity search (`fts` and `vss`).
- It is allowed to download/enable DuckDB extensions at runtime even if that requires network access (including on Windows).
- If DuckDB FTS/vector capabilities cannot be enabled/used, the server should **exit with an error** (no alternative backends in v1).

DuckDB compatibility contract (v1):

- The implementation must perform a startup self-test:
    - create/open the DuckDB database in the process-owned work directory,
    - install/load required extensions,
    - create schema,
    - insert 1–2 synthetic documents (including one synthetic embedding vector),
    - execute one FTS query and one VSS query.
- If any step fails, the server must exit with an error before serving MCP tools.
- Any SQL examples below are **illustrative** unless explicitly marked “validated in self-test”.

DuckDB schema and query shape (v1):

- Extensions: - `INSTALL fts; LOAD fts;` - `INSTALL vss; LOAD vss;`
- Tables (minimum): - `docs` (document-level): - `doc_id VARCHAR PRIMARY KEY` - `path VARCHAR` - `mtime TIMESTAMP` - `size BIGINT` - `title VARCHAR` - `text_all VARCHAR` - `embedding <VECTOR_TYPE>` where `<VECTOR_TYPE>` is a DuckDB representation validated for `vss` usage. `DIM` must be 3072 for `text-embedding-3-large`, and dimension mismatch must be treated as a fatal error (fail fast). - `index_meta` (single row): corpus roots, build timestamp, embedding deployment name, dimension, counts, plus `fd` version and discovery invocation.
- Full-text search (FTS): - Create index:
  `PRAGMA create_fts_index('docs', 'doc_id', 'title', 'text_all', stopwords = 'english', stemmer = 'porter', lower = 1, strip_accents = 1, ignore = '([^0-9A-Za-z_\-\./:])+' );` - Query candidates:
  `SELECT doc_id, score FROM (SELECT *, fts_main_docs.match_bm25(doc_id, :q) AS score FROM docs) WHERE score IS NOT NULL ORDER BY score DESC LIMIT :k_text;`
- Vector search (VSS): - Create HNSW index:
  `CREATE INDEX docs_embedding_hnsw ON docs USING HNSW (embedding) WITH (metric = 'cosine');` - Query candidates:
  `SELECT doc_id, array_distance(embedding, :qvec::FLOAT[DIM]) AS distance FROM docs ORDER BY distance ASC LIMIT :k_vec;`

## Index build pipeline

1. **Discovery**
    - Discovery is performed by invoking `fd` (rather than implementing recursive traversal in-process).
    - For each `--root`, run a command equivalent to:
      `fd --type file --follow --hidden --exclude .git -e md -e markdown . <root>`
      and optionally apply `--glob` / `--exclude` for `--include-glob` / `--exclude-glob`.
    - Rationale:
        - `fd` follows symlinks/junctions (`--follow`).
        - Ignore behavior is delegated to the installed `fd` implementation.
        - `--exclude .git` enforces the “always ignore `.git/`” rule.
    - Guardrails (v1):
        - Enforce a hard maximum number of discovered files (default: 100000). If exceeded, exit with an error.
          This should be implemented via `fd --max-results <N>` and a post-check on the returned list.
        - If `fd` is not available on PATH, exit with an error.
    - Precedence (v1):
        - The server does not attempt to override or re-implement ignore semantics.
        - `--include-glob` / `--exclude-glob` are passed to `fd`; their behavior and interaction with ignore rules follow `fd`'s implementation.
    - Root boundary enforcement (v1):
        - After enumeration, compute `realpath` for each candidate.
        - Skip a candidate if its `realpath` is not within at least one provided `--root`.
        - Define “within root” using the same normalization rules as `normalized_real_path` applied to both the candidate and each root (i.e., compare normalized real paths with a path-segment boundary).
    - Deduplicate files by **normalized real path**.
    - Record `path` (normalized real path), `mtime`, `size`, and a stable `doc_id` (SHA-256 of normalized real path).

2. **Parsing (document-level)**
    - Produce two derived text views:
        - `text_all`: includes code blocks.
        - `text_no_code`: excludes (or strongly down-weights) fenced code blocks.
    - Extract deterministic `code_signals` from fenced code blocks.
    - Store code blocks with stable identifiers for optional retrieval/display:
        - `code_block_id = hash(path + block_index + content_hash)` (example scheme)

    Markdown handling (v1):
    - Use a CommonMark-compatible Markdown parser/library.
    - Indented code blocks: best effort. If detected, include them in `text_all` and optionally in `code_signals`; otherwise treat as normal text.

3. **Embedding (document-level)**
    - Compute embeddings using Azure OpenAI embeddings.
    - Default embedding input: `text_no_code`.
    - For `mode=mixed` (future option): embed `text_no_code + code_signals`.
    - Store embedding model identity and dimensions in index metadata for observability.

    Embedding model (v1):
    - The embedding deployment must be backed by **text-embedding-3-large**.

    Embedding context limit (v1):
    - The embedding model context length is **8191 tokens**.
    - Token counting should use the model-compatible tokenizer (e.g., `tiktoken` with `cl100k_base`).

    Length imbalance mitigation for embeddings (no chunking):
    - Embed a **length-normalized representation** of the document (cap tokens/chars).
    - Suggested strategy: keep headings + first N tokens of prose (optionally plus tail), drop or down-weight code.

    Embedding input construction (v1 defaults):
    - Build `text_no_code` from the Markdown document with fenced code blocks removed (or strongly down-weighted).
    - Exclude YAML front matter (best effort) to reduce noise.
    - Construct a bounded `embedding_input` with a token budget (using `tiktoken` `cl100k_base`):
        - Total cap: **6000 tokens**.
        - Head: **5000 tokens** from the start (prefer title/headings, then prose blocks).
        - Tail: **1000 tokens** from the end (to capture conclusions/FAQs).
    - Because the embedding input is capped below 8191 tokens, v1 does not require any additional over-limit splitting logic.

4. **Full-text indexing (document-level)**
    - Index `text_all` for keyword lookup (error messages, commands, API identifiers).

5. **Vector indexing (document-level)**
    - Index document embeddings.

6. **No incremental updates (v1)**
    - Build once at startup; do not watch or update during the process lifetime.

7. **Failure policy (v1)**
    - Retry Azure OpenAI calls several times (with exponential backoff + jitter).
    - If indexing still fails after retries, **exit with error** (do not build a partial index).

## Handling length imbalance (bias control)

Problem: if documents have very different lengths, vector embeddings computed from raw long text can become less representative, and text scoring can skew toward verbose documents.

Mitigations (document-level):

1. **Length-normalized embedding input**
    - Do not embed the entire file verbatim.
    - Use a bounded representation (headings + capped prose) so long documents do not dilute semantics.

2. **Length-aware scoring adjustment (optional)**
    - If needed, apply a mild penalty based on document length:
      $$\text{score} = \text{hybrid\_score} \cdot \frac{1}{1 + \alpha \log(1 + \text{doc\_chars})}$$

3. **Diversification (optional)**
    - Apply a light MMR-like diversification step over final results.

## Hybrid retrieval strategy

### Candidate generation

- Retrieve `k_text` candidates from full-text search over documents.
- Retrieve `k_vec` candidates from vector search over document embeddings.

Defaults (v1):

- `top_k = 10`
- `k_text = 50`
- `k_vec = 50`

### Coarse reranking via RRF (rank fusion)

Use Reciprocal Rank Fusion (RRF) to combine multiple ranked lists (e.g., full-text rank list and vector rank list) into a single coarse ranking.

For each candidate document $d$, compute:

$$\mathrm{rrf}(d) = \sum_{i \in \{\text{text},\text{vec}\}} \frac{1}{k + r_i(d)}$$

Where:

- $r_i(d)$ is the 1-based rank of document $d$ in channel $i$ (missing documents contribute 0 for that channel),
- $k$ is a smoothing constant (typical values are 50–60).

Notes:

- RRF is robust when channel score scales differ and avoids manual weight tuning.
- This design does not use a separate rerank model for fine reranking.

Default RRF constant (v1):

- `k = 60`

### Result shaping

- Results are already document-level.
- Provide a snippet derived from `text_all` around the best-matching region (implementation detail).
- Snippet size limit (v1 default): **<= 800 characters**.

Snippet construction (v1):

- Use the rewritten keyword query (from the LLM rewrite stage) to build a token list.
- Find the first occurrence of any token (case-insensitive) in `text_all`.
- Return an 800-character window centered around the first hit (best effort).
- If no token is found, return the first 800 characters of `text_all`.

## Code blocks

- Code blocks are indexed in `text_all` for full-text search.
- For vector search, compute embeddings from `text_no_code` by default.
- Additionally compute and store `code_signals` (deterministic, local extraction) and retain `code_block_id` pointers for retrieval.
- Provide (future) query option `mode: {"docs","code","mixed"}`. Semantics: `docs` emphasizes prose; `mixed` includes code signals; `code` emphasizes code signals and relies on full-text for exact matching.

## Observability & operations

- Maintain an `index_meta` record:
    - corpus roots,
    - build timestamp,
    - embedding deployment id/name, dimension,
    - counts.
- Emit structured logs for:
    - index build duration,
    - docs indexed,
    - query latency breakdown (fts, vector, fusion).

## LLM-assisted query rewrite (required, minimal)

Use an Azure OpenAI chat/completions model. For v1, keep this minimal and use it for **query rewrite / expansion**.

Stages:

1. **Query rewrite / expansion**
    - Turn the user query into:
        - a keyword query for full-text, and
        - a semantic query for embeddings.
    - Expand abbreviations and normalize product/resource names.

Data minimization principle:

- It is acceptable (privacy/compliance) to send messages to Azure OpenAI. Prefer sending only the user query and small candidate snippets when possible.

Failure handling (v1):

- If query rewrite/expansion fails, `search` must return a tool error (no fallback to using the raw query).
- The error should clearly indicate that the rewrite stage failed (distinct from indexing/storage failures), and logs should include enough detail to troubleshoot.

## Risks and constraints

- DuckDB full-text/vector capabilities and packaging may require careful dependency choices on Windows.
- Azure OpenAI embeddings and chat models require network connectivity and Entra ID credentials.
- One-shot indexing means startup time is the key UX constraint.

## Lifecycle

- The index must be **ephemeral** and stored under a temporary directory.
- The temporary storage must be **deleted automatically when the process exits**.
