# Real User Audit Protocol

This record owns the exact operational observation boundary for the owner's
32-peer migration audit and execution/repair loop carried by
[Issue #1552](https://github.com/hcoona/three/issues/1552). The executor,
diagnostician and independent evidence reviewer consume it; the owner maintains
it when the subject or effects change. Without it, normal product use could
silently inherit the former fixture-only acceptance protocol.

The accepted [Delivery Wave](../../../../../docs/delivery-wave.md) grants work.
This protocol must separately merge before observation. It is not a successful
run report and does not reopen the former development acceptance campaign.
The [validation basis](validation.md) retains its evidence-level boundaries.

## Subject, environment and recorded identity

Use the C# product built once from an exact accepted `main` revision containing
the required repair and this protocol. Record the revision, application hash
and build identity, resolved configuration and Chinese goal hashes, and accepted
contract/protocol identities in private execution state before dispatch. Use
that unchanged binary for initialization, preflight, calibration, execution and
inspection. Changed relied-on inputs require matching receipts, not reused ones.

Use the owner's Windows host, root-selected .NET SDK, installed Git and existing
Copilot CLI. The accepted adapter selects official `GitHub.Copilot.SDK` 1.0.28
and its CLI 1.0.105 pin. After protocol acceptance and before relying on them,
record installed versions, inspect the pinned package's typed session,
metadata, limits and usage contracts, and recheck required installed CLI flags.
Pause affected work if an interface changed. Disable native automatic updates
and SDK runtime acquisition; do not install another backend or CLI.

Use only existing authentication, entitlement and default model configuration.
No account balance, personal usage, quota, credential or authentication-material
inspection is allowed. The owner accepts repository processing by this existing
model service and native soft-limit overshoot by an in-flight response.

## Repository, collaboration and output scope

Create a clean, named worktree of the recorded accepted revision, separate from
the owner's existing dirty checkout. Record checkout, index, tracked instruction
and original-file preservation baselines. Keep run state and outputs outside
the source checkout. The coordinator may create its owned worker worktrees,
branches, collaboration SQLite, process leases and native sessions.

Configure 32 workers, `planningSeconds: 0`, and one shared Chinese goal and
cooperation template. Workers select tasks, advisory claims, Board work and
peer review themselves; no fixed worker responsibilities, permanent leader or
central intelligent scheduler. The same goal covers the entire pinned migration
map and required behavior, not a preassigned partition. Keep
`candidateChecks`, `integrationChecks` and `finalChecks` empty: this is a
read-only audit, not a unit-test delivery gate.

Workers may read the declared target repository, this attempt's collaboration
state and the necessary pinned public upstream. They may run existing
credential-free managed checks as supporting evidence, not repeat the former
native acceptance campaign. They must not edit source, project records,
dependencies or workflows, commit/push, mutate Issues/PRs, publish, dispatch,
launch nested agent/model processes or inspect unrelated host/private/session
data. Existing trusted-host permission policy remains explicit; worktrees and
prompt instructions are not an OS permission sandbox. Stop on observed effects
outside the declared boundary.

The goal names one private Chinese final-report path inside this attempt's
owned output root. That report is an allowed write, not a source document.
Peers claim its preparation through normal cooperation to avoid concurrent
overwrites and publish matching content to the team channel under the title
`最终核验汇总`. Source identifiers, quoted evidence and paths keep their original
form. Repository records remain English.

## Continuing accounting and finite effects

Use the latest fully reconciled real-user audit's existing campaign ledger,
including all its previously reported spend. Before the first new dispatch,
record its exact private identity and a retained baseline snapshot, verify
paid admission and absence of uncertain reservations, and confirm the prior
coordinator and owned processes are inactive. Earlier retired ledgers,
including their unknown reservations, remain separate and unchanged. Do not
reclassify that historical uncertainty or initialize a new zero baseline.

Each newly initialized attempt has a 10,000-AI-Credit run allowance and a
1,800-second run deadline; the one continuing campaign has a cumulative
150,000-AI-Credit allowance. Calibration, ordinary turns, repeats, fresh
sessions and recovery all count in that same ledger. There is no separate
run-count quota; cumulative credit and per-run worker/time bounds are accident
fuses, not unlimited execution permission.

Retain the existing reservation, native limit readback, cumulative-delta and
ownership contracts. Require complete native-reported metrics before final
reconciliation or further paid admission; never infer exact spend from tokens,
elapsed time or account balance. Native limits are soft, not exact prepaid
ceilings. Unknown usage, unsupported limit application or ambiguous ownership
blocks replacement and further paid work. Preserve the affected reservation
and diagnose through the accepted non-dispatch reconciliation path.

## Execution and expected observations

1. **Prepare:** verify previous quiescence and campaign admission. Retain the
   exact source/build/configuration/goal identities and repository baseline.
   Initialize fresh owned attempt state pointing to the continuing ledger,
   not a cloned or reset active ledger.
2. **Preflight:** use the unchanged product's non-model operation to verify
   actual SDK/runtime/session identity, working directory, configured limits
   and worker-bound local MCP. No prompt, pending-work continuation, account
   query or paid replacement is permitted by this phase. Settle its processes.
3. **Calibrate:** reserve within the run/campaign allowances, verify the real
   session and 30-credit native soft cap, and send the existing tool-disabled
   `READY` calibration once under its two-minute deadline. Require complete
   cumulative usage and a matching actual build/configuration receipt before
   ordinary dispatch. Failed or unknown calibration is not automatically
   repeated; retain and diagnose its result first.
4. **Run:** start the actual foreground coordinator in psmux. Verify all 32
   ordinary workers actually dispatch, not merely start. Inspect product
   status and durable cooperation while it runs; retain observed task/claim,
   Board and peer-message activity, actual completed turns and interruptions.
   Do not inject a central task partition or treat progress counters as an
   audit conclusion. Observe the configured deadline, credit limits and stops.
   For the owner-requested autonomous follow-up, configure the accepted
   worker admission interval explicitly and retain its actual timing. Do not
   pause merely because an initial report exists or a historical file/message
   pair matches. Let peers perform review and latest-report synchronization
   until they finish their work or an existing finite/safety stop applies.
   Operator export is not evidence of autonomous report synchronization;
   retain any incomplete review or mismatched latest output as incomplete.
5. **Inspect and repair:** preserve each failure and establish process/usage
   settlement before any safe repetition. Diagnose only the exact owned run,
   leases, session identities and necessary private native diagnostics.
   Source findings, runtime observations, inferences and hypotheses remain
   distinct. Independently classify material findings before bounded repairs;
   changed requirements, architecture or recovery policy must separately
   become accepted prerequisites. Land and validate repairs through ordinary
   review/CI, then build the exact accepted revision for a new attempt.
   Existing pause, reconnect and explicit fresh-summary resume may be used
   only within their accepted ownership, identity and remaining-budget
   contracts after a real interruption; do not induce crash/recovery tests.
6. **Finish and reconcile:** require a substantive Chinese audit summary in
   team state and the declared private output. It names actual migration and
   requirement coverage, source-backed findings and independent
   classifications, checks actually run, missing coverage, unresolved
   disagreements and owner decisions, and a bounded semantic conclusion.
   Verify original-source preservation, no active coordinator or owned
   children, complete native usage and ledger reconciliation. Retain product
   delivery/check status truthfully; empty final checks are not acceptance.

Actual dispatch, meaningful cooperation, substantive audit output and complete
settlement establish only this operational journey. A running process,
deadline shutdown, mechanical finalization, test pass or agent assertion alone
does not. Missing audit coverage or unresolved findings remain visible; even a
successful operational run does not prove migration completeness, general
32-worker/backend support or the owner's semantic acceptance.

## Stops, retained evidence and cleanup

Stop dispatch and request controlled cancellation on owner stop, configured
deadline/credit exhaustion, unknown accounting, unverified native policy,
unexpected effects or ambiguous ownership. Never replace a live/unknown
writer, suppress a failure to obtain success, weaken a gate, retry a failed
observation blindly or reset state to repair accounting.

Keep configuration, goal, terminal transcript, SQLite/journals, source
worktrees, exact native associations, process leases, usage, outputs and
counterexamples in private execution state across iterations. The executor may
retain a snapshot of the continuing ledger before appending new work; snapshots
are evidence, never substitute active ledgers. Cleanup requires a separately
explicit decision after outcome/ownership inspection and targets only named
owned resources; no broad deletion or process-name killing.

Issue #1552 and its linked PRs retain exact source/build and accepted-authority
identities, commands/results, applicable rechecks, independent reviews and
triage, and sanitized outcomes/limitations. Do not publish private paths,
native/account/session identifiers, raw transcripts, authentication artifacts,
private source or personal account usage/balance. No release or proving
dispatch, credential/access change or automatic publication is authorized.
