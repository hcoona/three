## 1. Research decision

Use a breadth-first, then depth-first process:

1. Perform a preliminary but comprehensive static survey.
2. Let the project leader select valuable domains after reviewing comparable evidence.
3. Perform focused deep research only for selected domains.
4. Issue E0 to E3 authority only for a concrete, scoped operation.

Atlas v0 does not attempt to explain every variable, switch, or plugin object. It records every
observed structure and marks unexplained semantics as unknown.

## 2. Corpus and evidence boundary

Before copying, the project leader confirms a finite live-save discovery manifest, exact
fingerprint scope, and finite installed-definition roots and file-selection rules. The preliminary
survey then covers qualified read-only snapshots that are rehashed against private provenance
before each use:

- every existing `fileN.rpgsave`;
- `global.rpgsave`;
- `config.rpgsave`; and
- every included readable installed-game definition in that confirmed manifest.

Never:

- analyze against live originals;
- modify `steam_autocloud.vdf`;
- select only convenient or apparently representative slots;
- commit original or decoded saves;
- commit real values, names, narrative state, save hashes, or account metadata; or
- require new manual game actions to complete Atlas v0.

Existing snapshots may be compared automatically. Targeted single-action before-and-after game
experiments occur only after human value selection.

## 3. Atlas v0 completion

Atlas v0 is complete relative to its declared corpus, fingerprint, scanner, and schema when:

1. every expected corpus input has a scan result;
2. every valid in-scope baseline save decodes successfully unless the project leader approves a
   recorded scope narrowing;
3. every reachable decoded node is traversed;
4. every observed path, type, wrapper, identity, reference, and structural variant is recorded;
5. token, graph, scanner-visitation, input, and installed-definition denominators independently
   reconcile;
6. the in-scope baseline has zero opaque structural gaps;
7. every observation is semantically independently supported, disputed, or unknown;
8. committed records pass deny-by-default structural redaction validation; and
9. temporary decoded content is deleted after all Atlas v0 private-evidence-dependent reviews
   and cleanup is attested.

Unknown semantics do not block completion. Unsupported, unreadable, excluded, or opaque
in-scope content does block completion until the project leader narrows the declared scope.

This preliminary personal survey has no standalone calendar deadline. Its finite boundary is
the confirmed corpus and the structural completion rule above. Later focused research and
delivery work still require budgets and stop conditions.

## 4. Production workflow

```text
qualified, provenance-revalidated snapshot inputs
  -> deterministic structural scanner
  -> redacted observations and completeness report
  -> independent Agent semantic proposals
  -> evidence-based Agent cross-review
  -> generated structure and meaning views
  -> human value selection
  -> targeted controlled experiments
  -> operation specification and E0-E3 authority
```

The deterministic scanner owns structural facts. Agents cannot change those facts. A structural
disagreement becomes a scanner defect, not a semantic opinion.

Agents may:

- correlate observations with readable installed-game code and data;
- propose atomic semantic claims;
- cite exact source coordinates;
- identify competing interpretations;
- independently support, challenge, or request evidence; and
- propose the next discriminating experiment.

Agents receive only a schema-validated redacted envelope. Raw or decoded saves, private values,
private paths, private hashes, copied installed source, and uncontrolled prompt or log retention
are prohibited. Source reasoning uses safe coordinates and deterministic extracted facts by
default.

Atlas v0 Agent work uses a frozen deterministic annotation population. Each eligible item
receives no more than one author pass and one blind independent review pass. Items without safe
evidence candidates remain unknown without an Agent call. Agent agreement never becomes
accepted truth; it is recorded only as independently supported.

Agents may not:

- use majority voting;
- convert agreement into truth;
- assign confidence percentages as proof;
- issue E0 to E3 write authority; or
- silently replace an unknown with a plausible interpretation.

Human work is limited to:

- confirming corpus and fingerprint scope;
- confirming the exact discovery and installed-definition manifests before copy;
- approving any scope narrowing;
- selecting valuable domains;
- approving a targeted experiment;
- resolving a dispute only when a selected operation depends on it; and
- issuing or revoking operation authority.

## 5. Canonical logical model

The Atlas is one evidence system with two generated lenses. It is not another field tree.

### 5.1 Survey manifest

One frozen `SurveyManifest` records:

- survey scope and safe input aliases;
- compatibility fingerprint scope;
- scanner, schema, and redaction versions;
- input and structure denominators;
- scan failures and explicit gaps;
- generated-record digests; and
- decoded-data cleanup attestation.

The private alias map contains original paths and copy-verification hashes. It stays outside Git.

### 5.2 Observations

An `Observation` is an immutable scanner-owned structural fact:

- document role;
- typed raw locator;
- node and scalar type;
- object, array, wrapper, identity, and reference shape;
- presence and variation;
- privacy-safe traits; and
- survey and fingerprint scope.

Observation identity is deterministic from the survey, typed locator, and redacted structural
facts. A rendered dotted path or JSON Pointer is display syntax, not a semantic name.

### 5.3 Concepts

A `Concept` is a revisable possible meaning:

- hidden stable internal key;
- preferred human-readable label;
- definition and aliases;
- lightweight, many-to-many presentation facets; and
- revision and merge or split history.

Create concepts lazily. Do not create one for every node.

The internal key exists only for references and revision stability. No internal key
representation may become a heading, filename, URL, breadcrumb, capability key, semantic label,
or visible Atlas path.

### 5.4 Claims

A `Claim` is the only bridge between structure and meaning. It is an atomic,
subject-predicate-object proposition scoped to an exact survey or build.

Examples:

- an observation denotes a concept;
- two observations covary in the surveyed corpus;
- one value mirrors or derives another;
- a source symbol reads or writes a location; or
- a proposed invariant applies to a candidate operation.

Claims are append-only revisions. New evidence supersedes rather than overwrites a prior claim.

### 5.5 Evidence and reviews

An `Evidence` registration records a safe summary, type, exact scope, private payload reference,
validity state, and invalidation or deletion events.

A `Review` targets one exact claim revision and records:

- `supports`;
- `challenges`;
- `needs-evidence`; or
- a human `select`, `reject`, or `defer` decision.

The original claim and dissent remain visible after later resolution.

### 5.6 Value selection

A human `ValueSelection` record identifies:

- the exact Atlas snapshot;
- selected user outcome;
- relevant concepts, observations, and claims;
- decisive unknowns;
- expected benefit and alternatives;
- safety and maintenance concerns; and
- the permitted next research step.

It authorizes investigation, not writes or semantic truth.

### 5.7 Operation authority

Operation authority uses a separate append-only ledger:

- `OperationSpec` defines exact scope, read and write sets, parameter schema, preconditions,
  postconditions, refusal conditions, allowed diff, recovery, and required evidence.
- `AuthorityEvent` certifies or revokes one exact operation revision for one exact scope.

Only a human authority may issue E0 to E3. Agent annotations and Atlas evidence tags never grant
write authority automatically.

## 6. Evidence expression

Use composable evidence tags with direct citations:

- `observed-structure`;
- `source-linked`;
- `cross-save-correlated`;
- `runtime-confirmed`;
- `disputed`; and
- `unknown`.

These tags are not an ordinal confidence scale.

`cross-save-correlated` does not prove meaning, causality, authority, coupling direction, or a
write set. `runtime-confirmed` describes evidence, not release authority.

E0 to E3 belongs to an operation:

- E0: unsupported or blocked;
- E1: structural and static semantic basis only;
- E2: controlled disposable-copy research authorization;
- E3: exact operation, compatibility, safety, recovery, and independent evidence sufficient for
  its declared use.

## 7. Disagreement and invalidation

When agents disagree:

1. preserve every admissible interpretation, citation, and objection;
2. mark the affected claim `disputed`;
3. treat its operational meaning as unknown;
4. do not vote; and
5. request human adjudication only if a selected candidate depends on the dispute.

Evidence invalidation propagates to dependent claims. Claims lose tags whose required evidence
is no longer valid. An E2 or E3 operation that depends on unavailable evidence becomes
non-executable and receives a revocation event.

A new scanner, schema, corpus, game build, or relevant installed definition creates a new survey
scope. Old observations and claims remain historical and are not silently retargeted.

## 8. Persistence and privacy

Canonical, commit-safe records use schema-validated JSON or JSONL:

```text
survey-manifest.json
observations.jsonl
concepts.jsonl
evidence.jsonl
claims.jsonl
reviews.jsonl
value-selection.jsonl
operations/specs.jsonl
operations/authority-events.jsonl
schemas/
scanner-and-method/
```

Generated projections include:

- Markdown or HTML Atlas views;
- SQLite query cache;
- locator-to-concept crosswalk;
- unknown and dispute queue;
- local relationship views;
- completeness report; and
- value-selection brief.

Generated projections are disposable and must not become competing sources of truth.

Atlas v0 decoded private data exists only in a local temporary workspace. Keep each private
artifact only through its declared last-use review, then perform one final verified cleanup
before Atlas v0 acceptance. Commit only the scanner, method, schemas, redacted canonical Atlas,
and safe generated documentation chosen for review.

Later E2 or E3 before-and-after saves, runtime traces, and exact private fingerprints required
to audit an active operation remain protected outside Git until its support and appeal window
ends. Before E2 or E3, the project leader must set custody, backup, expiry, and destruction.

Do not copy game-owned labels or text into the committed Atlas. Use project-authored descriptive
labels, stable game IDs, raw locators, and source coordinates.

## 9. Generated human views

Generate two coordinated lenses from the same canonical records.

### 9.1 Structure

Navigate:

```text
document role -> raw hierarchy -> exact observation
```

Show exact locator, type, shape, presence, variation, linked claims, unknown state, and local
relations. Preserve physical occurrences and references rather than collapsing them into a
clean semantic tree.

### 9.2 Meaning and decisions

Show:

- revisable concepts and aliases;
- related raw observations;
- accepted and competing claims;
- evidence and counterevidence;
- unknowns and disputes;
- local coupling relations;
- candidate read-only and writable operations; and
- human value selections.

User-domain labels are presentation facets, not concept parents or identifiers. Final product
IA must follow selected user tasks rather than reproduce either Atlas lens.

## 10. Gold example

Atlas v0 first records two independent observations:

```text
slot :: party._gold
slot :: variables[215]
```

Both are initially `observed-structure` and semantically `unknown`.

Readable installed definitions may support a `source-linked` Gold claim for one or both
locations. Equality across the surveyed saves may support a `cross-save-correlated` claim.
Neither result proves:

- that variable 215 means Gold;
- that either field is authoritative;
- that both must be written;
- that their relationship is causal; or
- that a write is safe.

After the project leader selects Gold, focused experiments may compare:

1. changing `party._gold` only on a disposable copy;
2. changing variable 215 only;
3. changing both together; and
4. earning, spending, saving, loading, and saving again through the game.

A final `Set Gold` operation may safely write both locations without claiming which field is
authoritative, if the exact preconditions, write set, postconditions, allowed diff, game round
trip, recovery behavior, and compatibility scope reach E3.

## 11. Do not build now

Do not build:

- a graph database, RDF store, or ontology platform;
- a global graph UI;
- a rigid user-domain hierarchy;
- visible opaque Atlas IDs or canonical semantic slug paths;
- automatic concept creation, merge, or acceptance;
- confidence percentages or Agent voting;
- a second manually maintained crosswalk;
- an operation-only substitute for comprehensive Atlas v0;
- authoritative SQLite or hand-edited generated Markdown; or
- a writer before a scoped operation receives authority.

## 12. Decisions deferred to evidence

Atlas v0 does not decide:

- which observed domains are valuable;
- which leaves are authoritative, mirrored, derived, or merely correlated;
- which concepts should be merged or split;
- the final application navigation;
- the safe write set for any nonqualified operation; or
- whether future distribution is worthwhile.

Those decisions occur after the relevant structural, semantic, product-value, and runtime
evidence exists.
